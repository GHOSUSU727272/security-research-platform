# Эксплуатация

Очередь сохраняется до запуска. Запускайте `research run` после перезапуска:
задачи с истёкшей 30-секундной арендой подхватываются автоматически. Heartbeat —
раз в 5 секунд. Одновременно допускается один процесс scheduler на одну базу;
внутри него workers ограничивают число активных задач. Другие CLI могут добавлять
задачи и читать историю. `run` завершает работу после опустошения очереди.

Для автоматического перезапуска после падения можно использовать systemd:

```ini
[Unit]
Description=Authorized research queue

[Service]
Type=simple
User=research
WorkingDirectory=/opt/research-platform
ExecStart=/opt/research-platform/.venv/bin/research --config /etc/research.yaml run
Restart=on-failure
RestartSec=10
UMask=0077

[Install]
WantedBy=multi-user.target
```

Создание пользователя и установка unit выполняются администратором отдельно.
Не запускайте анализатор от root. Долгие тесты требуют увеличения timeout.
Ошибки одной задачи записываются и не останавливают остальные; после исчерпания
attempts задача остаётся failed. Проверяйте status и таблицу jobs в отчёте.

Логи ротируются: 5 MB × 6 файлов. Исходники/вывод могут содержать секреты:
храните state с правами 0700 и проверяйте отчёты перед передачей третьим лицам.
Результаты SQLite не удаляются автоматически. Для длительной эксплуатации
назначьте retention; делайте резервную копию через SQLite backup API или после
остановки всех писателей. Не копируйте только основной файл живой WAL-базы.

Индексация ограничена 10 000 файлами, примерно 64 MiB прочитанных данных,
100 000 рёбрами и max_file_bytes на файл. Порог проверяется между файлами;
последний файл может превысить общий порог. Усечение явно отмечено в coverage.
Симлинки исключаются; root должен быть доверенным и стабильным во время обхода.
Защиты от конкурентной подмены файлов враждебным процессом нет.

AST и локальные файловые операции синхронны внутри обработки одного файла;
async timeout кооперативный. Плагины и очень сложные AST могут задержать event loop.
Отчёт агрегирует историю в памяти; для больших историй нужны пагинация и retention.
Команды наследуют окружение и не имеют cgroup/сетевой изоляции. На Linux завершается
их process group, но демон, отделившийся через setsid, требует VM/cgroup cleanup.

Следующие production-этапы: process isolation для AST, миграции схемы, ограничение
объёма БД, пагинация отчётов, роли/аудит доступа, пакеты правил и нагрузочный soak-test.
