# SQLite: единственный writer Research Engine (v0.4.1)

## Первопричина

`knowledge_ingest.ingest()` держал курсор `SELECT * FROM jobs` открытым
между транзакциями. Независимые процессы FileAnalyzer и MemoryAnalyzer
одновременно записывали PluginFileCache/PluginProgress через собственные соединения.
После их commit курсор supervisor удерживал устаревший WAL snapshot.
`BEGIN IMMEDIATE` пытался повысить этот snapshot до записи и получал
`SQLITE_BUSY_SNAPSHOT` (517), отображаемый Python как `database is locked`.
Это воспроизводится двумя соединениями без внешнего процесса Research.
Повтор BEGIN или увеличение timeout не устраняет удерживаемый snapshot.
Семантика описана в [SQLite Isolation](https://www.sqlite.org/isolation.html).

## Решение и границы

Единственный writer исследовательского запуска — существующий supervisor и его
Store.db на одном event-loop thread. Планировщик, Timeline, Knowledge Engine,
Artifact Manager и checkpoints используют это же соединение. Worker'ы отправляют
операции checkpoint/cache в ограниченную asyncio-очередь supervisor через локальный
TCP endpoint. Consumer выполняет транзакции синхронно, без await внутри транзакции.
Таким образом, операции supervisor и consumer не могут перекрываться.

Endpoint слушает только 127.0.0.1 на случайном порту. Непредсказуемый токен
ограничен namespace задачи и именем плагина; передаются фиксированные операции,
не произвольный SQL. Число одновременно принимаемых сообщений, размер сообщения
и очередь ограничены. Worker ждёт подтверждения только после SQLite commit.
Ошибка persistence завершает задачу ошибкой, а не превращается в предупреждение
об анализируемом файле. Отмена прерывает ожидание; supervisor обслуживает очередь
до завершения worker'ов. При смерти supervisor неподтверждённые операции могут
быть повторно вычислены при resume; подтверждённый cache уже находится в SQLite.
Новая сессия выдаёт новые токены. Записи cache/progress идемпотентны по прежним PK.

Plugin API и схема SQLite сохраняются. Context получает необязательные поля
endpoint/token, выдаваемые только при запуске процесса; в ResearchTasks и экспорт
они не сохраняются. Standalone/legacy plugin execution сохраняет локальный backend
checkpoints. Сторонние плагины должны использовать общий checkpoint client;
произвольный прямой SQL стороннего расширения не контролируется этим протоколом.
Отдельные CLI-команды управления по-прежнему используют короткие SQLite-транзакции;
WAL допускает их сериализацию. Решение не обещает устранить блокировки от внешнего
ПО, удерживающего собственную write-транзакцию.

Импорт Knowledge выполняется постранично по ID: закрываем курсор списка ID,
затем начинаем write-транзакцию и перечитываем конкретный job и его отметку импорта.
Ни один read cursor не переносится через границу write-транзакции. Память ограничена
страницей ID и одним результатом; успешные импорты фиксируются отдельно и не
повторяются после сбоя. Курсор сравнения dynamic runs закрывается даже при break.

## Проверка

`tests/test_sqlite_writer.py` содержит девять проверок:

- Детерминированное воспроизведение старого SQLITE_BUSY_SNAPSHOT (517).
- 130 импортов через несколько страниц ID; независимое соединение делает commit
  непосредственно перед каждым BEGIN, при busy_timeout=0.
- Rollback одного job с сохранением ранее импортированных результатов.
- Подтверждение commit, атомарность sample и изоляция namespace/token;
  тест запрещает клиенту IPC вообще открывать sqlite3.connect.
- Четыре реальных процесса Config/YAML/Strings/Logs, синхронизированные барьером.
  168 файловых checkpoints, параллельный WAL reader, импорт и progress/checkpoints;
  busy_timeout=0, одна попытка на задачу, проверка нулевых ошибок/предупреждений,
  одного потока записи, четырёх разных PID, integrity_check и foreign_key_check.
- Отмена после подтверждённого файла и использование cache после открытия
  нового Store и нового endpoint supervisor.
- Ошибка persistence завершает задачу вместо предупреждения разбора.
- Незавершённый отправитель не блокирует shutdown.
- Потеря endpoint не переключает worker на независимую запись SQLite.
